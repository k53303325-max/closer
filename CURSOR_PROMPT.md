# Closer — промты для Cursor

## Как пользоваться

1. Распакуйте архив — это корень будущего репозитория. Откройте папку в Cursor.
2. Правила `.cursor/rules/closer.mdc` подхватятся сами: Cursor будет помнить их в каждом чате.
3. Работайте по этапам ниже. **Один этап — один новый чат в режиме Agent.** Скопируйте промт этапа целиком и вставьте в чат.
4. В конце каждого этапа Cursor должен прогнать тесты. Проверьте руками то, что указано в «Проверить», и только потом переходите дальше.
5. Если Cursor предлагает изменить шаблон `.docx` или текст договора — откажитесь: это делает только автор.

Что уже есть в папке и работает:
- `templates/uslugi/contract.docx`, `act.docx` — шаблоны автора; поля размечены метками.
- `templates/uslugi/fields.json` — какие поля, откуда берутся, какие вопросы задавать.
- `closer/documents/docx_fill.py` — заполнение шаблона и PDF через LibreOffice.
- `closer/documents/parties.py` — строка стороны, реквизиты и НДС по статусу.
- `tools/fill_example.py`, `tests/test_docx_fill.py` — проверка, что шаблоны заполняются.
- `docs/spec.md` — ТЗ, `docs/pep_offer.md` — соглашение о ПЭП.

## Этап 0. Каркас (1–2 дня)

```
Прочитай docs/spec.md целиком, затем templates/uslugi/fields.json и код в closer/documents/.

Создай каркас проекта по разделу 10 спецификации:
- pyproject.toml (Python 3.12): aiogram 3, sqlalchemy[asyncio] 2, asyncpg, alembic, redis, arq, lxml, pydantic-settings, httpx, cryptography, pytest, pytest-asyncio, ruff.
- Структура папок как в разделе 10. Существующие файлы в closer/documents/, templates/, tests/, tools/ не меняй.
- docker-compose.yml: bot, worker, postgres:16, redis:7. Образ приложения на python:3.12-slim с установленными libreoffice-writer и шрифтами (fonts-crosextra-carlito, fonts-dejavu) — шаблоны используют шрифт Carlito.
- config.py на pydantic-settings, .env.example со всеми переменными (BOT_TOKEN, DATABASE_URL, REDIS_URL, GIGACHAT_AUTH_KEY, SMS_PROVIDER, SMS_API_KEY, S3_*, PD_ENCRYPTION_KEY, ADMIN_TG_IDS).
- Бот запускается в режиме polling и отвечает на /start заглушкой.
- texts/ru.yaml и загрузчик текстов.
- ruff и pytest настроены; существующие тесты проходят.

В конце: запусти pytest и `python tools/fill_example.py` внутри контейнера и покажи вывод.
```
**Проверить:** `docker compose up` поднимается, бот отвечает на /start, в `out/example/` появились PDF.

## Этап 1. База данных и профиль (3–4 дня)

```
Реализуй по docs/spec.md разделы 3, 8 и 9:
1. Модели SQLAlchemy и первая миграция Alembic для всех таблиц раздела 8. Для audit_log — триггер, запрещающий UPDATE и DELETE. Поля passport_enc и address_enc — шифрование AES-GCM ключом PD_ENCRYPTION_KEY (отдельный модуль crypto.py с тестами).
2. Сервис audit: append_event(document_id, event, actor, payload, doc_sha256), считает prev_hash/record_hash цепочкой; функция verify_chain(document_id). Тесты на цепочку.
3. Первый вход: экран соглашения о ПЭП ровно как в docs/pep_offer.md, раздел «Как пользователь его принимает» (кнопка-галочка ☐/☑ + «Продолжить», без отметки — всплывающее «Отметьте согласие»). Запись в consents и событие offer_accepted с SHA-256 текста docs/pep_offer.md.
4. Запрос контакта (reply-кнопка «Поделиться контактом»), принимаем только собственный контакт пользователя (contact.user_id == from_user.id).
5. Профиль /profile: сначала статус кнопками (физлицо, самозанятый, ИП, ООО), затем только поля этого статуса по таблице раздела 3, по одному вопросу, с валидацией (ИНН с контрольной суммой, ОГРН/ОГРНИП, паспорт 4+6 цифр). Для ООО — должность и основание кнопками, для ИП/ООО — режим НДС кнопками.
6. Профиль преобразуется в closer.documents.parties.Party — напиши адаптер и тест, что для каждого статуса party_line и party_details собираются без None.
Тексты — в texts/ru.yaml, простым языком.
```
**Проверить:** пройти первый вход и профиль за каждый из четырёх статусов; в БД паспорт зашифрован; UPDATE в audit_log падает.

## Этап 2. Черновик договора (4–5 дней)

```
Реализуй создание договора по docs/spec.md разделы 2 (шаги 1–4) и 4:
1. integrations/gigachat.py: класс LLMClient с методом extract(text) -> dict, реализация для GigaChat API (модель GigaChat Lite, ответ строго JSON). В промпт ИИ передаётся только текст описания сделки. Схема ответа: services (дательный падеж, продолжает «оказывает услуги по …»), term, price (число), payment (prepay|postpay|split|null), unsupported (bool). Сделай FakeLLM для тестов.
2. /new: вопрос «Вы оказываете услуги или заказываете?» (определяет, кто заказчик, кто исполнитель) → просьба описать сделку одним сообщением → extract → вопросы только по пустым полям, формулировки из fields.json → ask. payment всегда кнопками, тексты вариантов дословно из fields.json → payment.options.
3. Нормализация в коде: price в «45 000», term в «до DD.MM.YYYY» или «с … по …» (относительные сроки — от сегодняшней даты по Москве).
4. Карточка договора: все поля + кнопки «Изменить поле», «Подписать и отправить», «Удалить». PDF-черновик: заполнить templates/uslugi/contract.docx через fill_docx; поля второй стороны, пока она не подключилась, заполняются текстом «будет заполнено второй стороной»; на PDF водяной знак «ЧЕРНОВИК» (наложить на PDF средствами pypdf, docx не трогать).
5. Номер договора CL-YYYY-NNNNNN из последовательности; date — дата создания версии.
6. Каждая генерация — новая запись document_versions с values (jsonb), pdf_path, pdf_sha256.
7. Проверка лимита: первые 3 договора инициатора бесплатно (users.free_contracts_used); на четвёртом — заглушка «Скоро здесь будет оплата», реальную оплату сделаем на этапе 5.
Тесты: извлечение с FakeLLM, нормализация суммы и срока, генерация версии.
```
**Проверить:** «Сделаю логотип за 45 тысяч до конца ноября, половина вперёд» → бот спрашивает только недостающее → PDF совпадает с шаблоном автора, подставлены верные значения.

## Этап 3. Подписание (4–5 дней)

```
Реализуй подписание по docs/spec.md разделы 2 (шаги 5–8) и 5:
1. integrations/sms.py: интерфейс SmsGateway.send(phone, text) -> sms_id; реализации для SMSC.ru и SMS Aero (выбор по SMS_PROVIDER) и FakeSms для тестов.
2. services/sign.py: request_code(version, user) и confirm_code(version, user, code) по правилам раздела 5 (6 цифр, хеш с солью, 5 минут, 5 попыток, 60 с между отправками, 5 СМС в час). Перед отправкой кода бот показывает PDF и первые 8 символов SHA-256. События code_sent и signed в журнал.
3. Приглашение: токен 32 байта (в БД только хеш), ссылка t.me/<bot>?start=c_<token>, срок 7 дней, привязка к первому открывшему. Вход контрагента: кто приглашает, вид и сумма → соглашение о ПЭП → контакт → профиль (если пуст) → новая версия PDF с его данными → «Подписать» / «Предложить правку» / «Отказаться».
4. Правка: выбор поля → новое значение → новая версия, подписи предыдущей версии недействительны, инициатор получает уведомление и подписывает заново.
5. После двух подписей: событие finalized; documents/signing_sheet.py генерирует отдельный PDF «Лист подписания» по разделу 5 (используй reportlab или HTML→PDF через LibreOffice — без изменения подписанного PDF); обе стороны получают подписанный PDF и лист подписания.
6. /verify: принимает PDF, считает SHA-256, отвечает по журналу.
Тесты: полный сценарий подписания на FakeSms и FakeLLM, сброс подписи после правки, verify.
```
**Проверить:** два своих аккаунта Telegram — договор от создания до двух PDF; хеш в листе подписания совпадает с `sha256sum` файла; правка сбрасывает подпись.

## Этап 4. Акт, напоминания, оплата сторон (3 дня)

```
Реализуй docs/spec.md раздел 6 и статусы раздела 7:
1. Акт: кнопка «Создать акт» у исполнителя в карточке подписанного договора; поля из fields.json → act_copies_from_contract; start и end с кнопкой «Оставить» (значения по умолчанию из fields.json). Заполнение templates/uslugi/act.docx, подписание тем же сервисом sign. У заказчика — «Подписать» и «Есть недостатки» (обязательный текст → исполнителю).
2. Молчание 5 дней после доставки акта: событие act_silent_accept, статус completed, сообщения обеим сторонам.
3. worker (arq): задача раз в 10 минут обрабатывает reminders по таблице раздела 6; reminders создаются и отменяются при смене статусов.
4. Кнопки «Оплатил» / «Оплату получил» с событиями paid_marked / payment_received; самозанятому — напоминание про чек в «Мой налог».
5. /my: список документов с фильтром по статусу, по 10 на страницу.
Тесты: расписание напоминаний, приёмка молчанием, переходы статусов.
```
**Проверить:** акт подписывается; если заказчик молчит (для теста сократите срок в конфиге), договор становится «Исполнен».

## Этап 5. Запуск (2–3 дня)

```
Подготовь запуск:

4. Удаление аккаунта /delete_me: подтверждение, deleted_at, через 30 дней задача воркера уничтожает данные и файлы пользователя (документы, где есть вторая сторона, — по решению из раздела 11 спецификации; до решения не удалять журнал).
5. Sentry для ошибок, логи без ПДн.
6. README с инструкцией развёртывания.
```
**Проверить:** оплата Stars в тестовом режиме, восстановление бэкапа на чистой БД, удаление аккаунта.

## Когда автор пришлёт новые шаблоны (подряд, поставка)

```
Добавь новый вид договора <вид> по образцу templates/uslugi:
1. Автор положил templates/<вид>/contract.docx и act.docx. Выведи список меток полей (template_fields) и сравни с uslugi.
2. Создай templates/<вид>/fields.json по образцу uslugi, вопросы и форматы — для новых полей спроси у меня.
3. Добавь выбор вида договора в /new и классификацию в LLMClient. Текст шаблонов не меняй.
4. Расширь tests/test_docx_fill.py на новый вид и запусти tools/fill_example.py с примером.
```
